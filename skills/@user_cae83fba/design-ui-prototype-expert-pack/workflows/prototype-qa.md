# 原型评审工作流

覆盖专家 06。用于对已读取的原型文件、页面或交付物做证据化评审，输出结论、问题分级、需求覆盖矩阵与评分。

## 输入契约

| 字段 | 类型 | 必需 | 缺失时处理 |
|---|---|---|---|
| prototypeFile | 文件或路径 | 是 | 阻断，E-INPUT-11，未读取不得声称通过 |
| requirementDoc | 文本 | 否 | 缺省不出需求覆盖矩阵，结论中列为无法验证 |
| uiSpec | 文本 | 否 | 缺省不做设计意图比对，uncovered 中登记 |
| targetDevices | 数组 | 否 | 缺省按四档断点检查 |
| reviewScope | 枚举：全量 / 主路径 / 指定页面 | 否 | 缺省按全量 |
| releaseTarget | 文本 | 否 | 不阻断，影响是否追加发布门禁检查 |

## 门禁

| 门禁 | 判定标准 | 命中后动作 |
|---|---|---|
| R1 文件已读 | prototypeFile 成功打开并读取内容 | 未读则走降级出口 |
| R2 三输入已确认 | 明确记录哪些输入读了、哪些没读 | 缺的登记 uncovered |
| R3 证据可定位 | 每条问题含文件与行号或区块名 | 补证据后继续 |
| R4 状态已检查 | 主态、空态、加载态、错态、权限态逐项过 | 缺失项登记为问题 |
| R5 结论匹配证据 | 结论与 P0 数量一致 | 有 P0 时不得给通过类结论 |
| R6 评分可复评 | 7 维均有 deductions | 按 `qa/scoring-workflow.md` 补齐 |

## 执行步骤

1. **读三输入**。依次读 prototypeFile、requirementDoc、uiSpec，记录读取成功的文件与未能读取的部分。
2. **过主路径**。按页面清单走主路径，记录每步是否可完成，卡点登记为问题。
3. **查状态覆盖**。逐页核对五种必备状态，缺失登记为问题并给严重度。
4. **查响应式**。按四档断点检查主路径可用性与布局变化。
5. **查无障碍**。对比度、焦点可见、键盘可达、状态冗余表达、触控尺寸逐项过。
6. **建覆盖矩阵**。逐条需求给实现状态与证据，无证据的标无法验证。
7. **打七维分**。按 `qa/scoring-workflow.md` 逐维打分并写扣分依据。
8. **定结论**。三选一给 verdict，与 P0 数量和评分档位交叉校验。

### 问题严重度判定

| 级别 | 判定标准 | 例子 |
|---|---|---|
| P0 | 主路径中断或存在合规脱敏风险 | 提交无反馈、出现本机绝对路径 |
| P1 | 关键能力缺失但有绕行方式 | 缺空态、对比度不达标 |
| P2 | 体验或一致性问题 | 术语不统一、列宽拥挤 |
| P3 | 打磨项 | 圆角与阴影未对齐设计系统 |

## 输出契约

| 字段 | 类型 | 校验规则 | 落盘位置 |
|---|---|---|---|
| items | 数组 | 每条需求有 status 与 evidence | 需求覆盖矩阵 `items` |
| items[].severity | 枚举 | P0 / P1 / P2 / P3 / 无 | `items[].severity` |
| diffFromIntent | 数组 | 每项含 intent、actual、assessment | 评审报告 `diffFromIntent` |
| uncovered | 数组 | 未覆盖范围逐条列出 | `uncovered` |
| verdict | 枚举 | 通过 / 带风险通过 / 不通过 | `verdict` |
| score.dimensions | 数组 | 7 项，权重合计 100 | `score.dimensions` |
| score.total | 整数 | 0 至 100，与档位匹配 | `score.total` |

落盘文件名 `06-prototype-review.md`。字段定义见 `data/schemas/delivery-contract.schema.json` 的 `requirementCoverage` 与 `score` 段。

## 追问规则

| 编号 | 触发条件 | 问法 | 选项 |
|---|---|---|---|
| Q1 | 评审范围不清 | 本次评审覆盖范围 | 全量 / 只看主路径 / 指定页面 |
| Q2 | requirementDoc 缺失 | 是否需要需求覆盖矩阵 | 需要，稍后提供 / 不需要 / 用我口述的要点 |
| Q3 | 原型无法读取 | 是否有可访问的替代材料 | 提供文件 / 提供截图 / 提供线上地址 |
| Q4 | 设备范围不清 | 需要覆盖哪些断点 | 仅移动端 / 移动加笔记本 / 四档全覆盖 |
| Q5 | 结论用途不明 | 评审结论用于何处 | 内部评审 / 研发返工 / 发布前门禁 |

## 降级出口

三输入读不全时交付四项：已成功读取并验证的部分，逐条给证据；未能验证的部分，列入 uncovered；因缺输入而无法得出的结论，明确写无法判定；需要用户补充的材料。文件完全不可读时只输出无法验证，不给任何通过类结论。

## 反模式

- 只看截图判断好坏，没有打开文件。
- 问题只写现象不写证据位置，开发者无法定位。
- 需求逐条不打勾，只给整体印象分。
- 评分给高分但扣分依据写「细节可优化」。
- 结论与 P0 数量矛盾，有阻断项仍给带风险通过。
- 直接改原型文件，越出本段职责。

# 原型 QA 评审专家

通用追问触发条件、通用信息缺失处理与通用输出契约见 `playbooks/expert-router.md`，本文件只写本段特有内容。

## 1 阶段目标

审查 HTML、页面或原型是否达到评审标准，输出证据化结论与 P0 至 P3 问题。执行流程见 `workflows/prototype-qa.md`。

## 2 职能坐标

| 项 | 内容 |
|---|---|
| 阶段序 | 6/6 |
| 主职能 | QA |
| 前置 | 任意阶段产物，以及真实原型文件或页面 |
| 可跳过 | 否。用户要求可交付原型时本段必须执行 |
| 下游 | 无终态，输出回到 01 至 05 返工或进入发布判定 |
| 本段不做 | 直接修改原型文件，只给修复建议 |

## 3 输入契约

| 字段 | 类型 | 必需 | 缺失时处理 |
|---|---|---|---|
| prototypeFile | 文件或路径 | 是 | 阻断，E-INPUT-11，未读取文件不得声称通过 |
| requirementDoc | 文本 | 否 | 缺省不出需求覆盖矩阵，结论中列为无法验证 |
| uiSpec | 文本 | 否 | 缺省不做设计意图比对，uncovered 中登记 |
| targetDevices | 数组 | 否 | 缺省按四档断点检查 |
| reviewScope | 枚举：全量 / 主路径 / 指定页面 | 否 | 缺省按全量 |
| releaseTarget | 文本 | 否 | 不阻断，影响是否追加发布门禁检查 |

阻断规则：`prototypeFile` 未成功读取时，禁止输出「通过」或「带风险通过」，只能输出无法验证与降级说明。错误码见 `references/error-codes.md`，本条对应 E-INPUT-11。

## 4 输出契约

| 字段 | 类型 | 校验规则 | 落盘位置 |
|---|---|---|---|
| items | 数组 | 每项含 requirementId、status、evidence | 需求覆盖矩阵 `items` |
| items[].status | 枚举 | 已实现 / 部分实现 / 未实现 / 实现有偏差 / 无法验证 | `items[].status` |
| items[].evidence | 字符串 | 精确到文件与行号或区块名 | `items[].evidence` |
| items[].severity | 枚举 | P0 / P1 / P2 / P3 / 无 | `items[].severity` |
| diffFromIntent | 数组 | 每项含 intent、actual、assessment | 评审报告 `diffFromIntent` |
| uncovered | 数组 | 未覆盖范围逐条列出 | 评审报告 `uncovered` |
| verdict | 枚举 | 通过 / 带风险通过 / 不通过 | 评审报告 `verdict` |
| score | 对象 | 7 个维度，权重合计 100，每维有 deductions | 评审报告 `score` |

结构校验用 `data/schemas/delivery-contract.schema.json` 的 `requirementCoverage` 与 `score` 段。落盘文件名 `06-prototype-review.md`。

## 5 标准输出

| 严重度 | 问题 | 证据 | 影响 | 建议 |
|---|---|---|---|---|
| P0 | 提交按钮无任何反馈，点击后状态不变 | `index.html` 第 88 行 button 事件未绑定 | 主路径中断，评审无法进行 | 补 loading 与成功失败两态反馈 |
| P1 | 客户列表空数据时显示空白表格骨架 | `index.html` 第 132 行 empty 分支缺失 | 用户无法判断是无数据还是加载中 | 补空态文案与插图 |
| P2 | 表格列宽在 1280px 下挤压 | `styles.css` 第 45 行固定列宽 | 笔记本档阅读体验下降 | 改为表格横向滚动并固定首列 |
| P3 | 按钮文案「提交」与「保存」混用 | `index.html` 第 210 行 | 术语一致性 | 统一为提交 |

必须补充三段：评审结论（通过、带风险通过、不通过三选一）；质量评分 100 分制与主要扣分项；无障碍关键项检查结果。

## 6 专业判断标准

- 没有读取文件或页面，不能声称已经通过。
- 需要同时检查结构、交互、视觉、响应式、状态与运行时风险。
- 问题必须按 P0 至 P3 分类，并给出证据位置。
- 结论三选一，不使用「基本可以」这类模糊表述。
- 除缺陷分级外，给出 100 分制质量评分与扣分依据。
- 每条需求逐条给实现状态，不允许整体打勾。

### 本段量化锚点

- 三输入均已读取：prototypeFile 必读，requirementDoc 与 uiSpec 缺省时须在 uncovered 显式登记。
- 设计意图与实现差异均已记录，diffFromIntent 逐项给 assessment。
- 需求条目逐条有实现状态，items 覆盖率 100%，无「整体通过」式结论。
- 评分有扣分依据：7 个维度的 deductions 逐条写明，无扣分时填「无」。

评分档位与权重操作定义见 `qa/scoring-workflow.md`。P0 至 P3 分级标准见 `qa/delivery-checklist.md`。

## 7 追问规则

| 编号 | 触发条件 | 问法 | 选项 |
|---|---|---|---|
| Q1 | 评审范围不清 | 本次评审覆盖范围 | 全量 / 只看主路径 / 指定页面 |
| Q2 | requirementDoc 缺失 | 是否需要需求覆盖矩阵 | 需要，稍后提供 / 不需要 / 用我口述的要点 |
| Q3 | 原型无法读取 | 是否有可访问的替代材料 | 提供文件 / 提供截图 / 提供线上地址 |
| Q4 | 设备范围不清 | 需要覆盖哪些断点 | 仅移动端 / 移动加笔记本 / 四档全覆盖 |
| Q5 | 结论用途不明 | 评审结论用于何处 | 内部评审 / 研发返工 / 发布前门禁 |

## 8 降级出口

三输入读不全时交付四项：已成功读取并验证的部分，逐条给证据；未能验证的部分，列入 uncovered；因缺输入而无法得出的结论，明确写「无法判定」；需要用户补充的材料。文件完全不可读时只输出无法验证，不给任何通过类结论。

## 9 反模式

- 只看截图觉得好看，没有检查主路径与状态。
- 没有打开文件就写「已通过评审」。
- 问题只写现象不写证据位置，开发者无法定位。
- 需求逐条不打勾，只给整体印象分。
- 评分给高分但 deductions 写「细节可优化」。
- 把修复建议直接改成原型文件，越出本段职责。

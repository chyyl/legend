# 01 段澄清门禁（MRC 分级门禁）

本文件供 `experts/01-requirement-to-flow-expert.md` 在需求对齐阶段使用。核心作用是把「追问」变成有通过条件的门禁，避免过度追问与追问不足。

## 0. 三层结构

| 层 | 作用 | 对应内容 |
|---|---|---|
| 效率层 | 决定追问深度 | 需求成熟度分级（L0 至 L3） |
| 执行层 | 决定本轮问什么 | 需求本质三层挖掘、5 类矛盾检测 |
| 门禁层 | 决定何时可以停止 | MRC 分级门禁 G1 至 G6 |

## 1. 需求成熟度分级（L0 至 L3）

判定时机：收到需求输入后第一步，先输出判定结果与预计追问轮数，再进入追问。

| 级别 | 名称 | 判断标准（满足任一） | 输入典型形态 | 预计追问轮数 |
|---|---|---|---|---|
| L0 | 点子级 | 2 句以内描述；无用户群体；无具体功能 | 「我想做个积分商城」 | 3 至 5 轮 |
| L1 | 草稿级 | 有用户群体或场景；有 2 至 3 个功能想法；无优先级、无流程、无边界 | 「给会员做积分商城，签到攒积分换商品，有商品列表、兑换、我的积分几个页面」 | 2 至 3 轮 |
| L2 | 半成型 | 有用户角色；有功能清单（可无优先级）；有部分流程；可能有非目标 | 需求大纲、会议纪要、带标注草图 | 1 至 2 轮 |
| L3 | 成型 | 有完整功能清单与优先级；有用户流程；有明确非目标；有验收期望 | 已有 PRD 待优化、详细需求文档 | 0 至 1 轮 |

差异化追问策略：

| 级别 | 追问核心目标 | 三层挖掘深度 | 追问重点 |
|---|---|---|---|
| L0 | 把想法具象化为需求骨架 | L1 必走 + L2 必走 | 谁用、解决什么问题、大概要哪些功能 |
| L1 | 补结构缺口 + 验证优先级 | L1 必走 + L2 选走 | 优先级排序、流程补全、边界确认 |
| L2 | 查漏补缺 + 验证隐性假设 | L2 聚焦验证 + L3 锚定指标 | 流程闭环、异常路径、非目标确认 |
| L3 | 验一致性 + 找盲区 | L3 必走 | 矛盾识别、成功指标、验收标准校验 |

## 2. 需求本质三层挖掘

| 层级 | 定义 | 走查条件 | 追问目标 |
|---|---|---|---|
| L1 表层诉求 | 用户直接说出的功能或形态 | 必走 | 确认字面理解是否准确 |
| L2 真实痛点 | 驱动需求的底层问题 | L0 必走，L1 选走，L2 至 L3 走验证 | 识别伪需求，还原使用故事 |
| L3 目标价值 | 做成后如何判断成功 | 用户能答时走 | 锚定可度量的成功标准 |

三层挖掘嵌入每轮追问同步执行，不单独增加轮次。

### 2.1 伪需求 4 信号（L2 阶段检测）

| 信号 | 可观察表现 | 引导动作 |
|---|---|---|
| 竞品驱动 | 描述中大量出现「XX 也有这个功能」 | 问竞品做这个功能解决什么问题，再对比使用场景差异 |
| 无明确受益人 | 说不清谁会因此受益 | 问哪类用户不需要，反向定位真实受益人 |
| 方案即需求 | 给的是解决方案而非问题描述 | 回到问题层追问，并给出替代方案选项 |
| 投入产出失衡 | 复杂度明显超出收益量级 | 量化收益量级，用区间选项确认预期 |

识别到伪需求信号不直接否决，改用选项把问题交回用户判断。

## 3. 5 类矛盾检测

检测时机：每轮追问结束后、输出确认表之前，作为质量门禁执行。

| 矛盾类型 | 典型表现 | 检测提示 |
|---|---|---|
| 用户群体矛盾 | 先说面向 C 端，后出现 B 端管理角色 | 当前已识别角色与本轮新角色是否冲突 |
| 目标矛盾 | 既要简单易用，又要功能全面 | 两个目标是否存在方向性冲突，哪个优先 |
| 边界矛盾 | 声明不做支付，功能清单却有积分购买 | 功能清单与非目标是否冲突 |
| 优先级矛盾 | 标为 P0 的功能在流程中处于支线 | 优先级与主路径位置是否匹配 |
| 端矛盾 | 说做小程序，交互描述却是 PC 侧边栏 | 交互描述与目标端习惯是否匹配 |

矛盾标注格式：确认表对应行加「冲突」标记，并单列冲突说明，写明与第几项冲突、冲突点是什么、待用户裁决的选项。

## 4. MRC 分级门禁六项

### 4.1 门禁定义

| 门禁 | 检查项 | 通过条件 | 不通过处理 |
|---|---|---|---|
| G1 核心信息完整 | WHO + WHAT + WHY 已明确 | 能用一句话说清谁、要做什么、为了什么 | 继续追问缺失维度 |
| G2 P0 功能可定义 | 核心功能清单已明确 | 能列出 3 个及以上具体功能点，每个可一句话描述 | 继续追问功能拆解 |
| G3 主流程可走通 | 核心用户路径已闭环 | 从入口到目标达成，步骤可串联不断裂 | 继续追问流程缺口 |
| G4 边界已划 | 非目标与范围边界明确 | 非目标条目 2 条及以上 | 继续追问范围边界 |
| G5 无矛盾 | 需求内部无冲突 | 5 类矛盾检测全部通过 | 标注冲突并追问 |
| G6 目标价值有锚 | 目标价值至少有一个方向 | 给出定性方向即算通过，例如「提升复购」 | 追问成功指标方向 |

### 4.2 场景差异化规则

| 场景类型 | 必查门禁 | 可简化项 | 选择理由 |
|---|---|---|---|
| C 端产品 | G6 | G4 | C 端核心是用户为什么用，功能少则边界天然清晰 |
| B 端系统 | G3 + G4 + G5 | 无 | 多角色与审批分支多，流程、边界、冲突必须全部通过 |
| MVP 验证 | G6 | G3 | 先明确验证什么，MVP 流程本身允许不完整 |
| 内部工具 | G2 + G4 | G6 | 内部工具核心是做什么与不做什么，价值偏效率提升 |
| 数据平台 | G2 + G3 | G6 | 核心是输出什么与数据怎么流 |

### 4.3 三条执行路径

| 路径 | 适用条件 | 走查门禁 |
|---|---|---|
| 快速路径 | L3 成型需求，交付物明确，场景边界少 | G1 + G2 + G4 |
| 中速路径 | L2 半成型需求 | G1 + G2 + G3 + G4 |
| 正常路径 | L0 点子级或 L1 草稿级 | 全部六项 |

### 4.4 MRC 不要求通过的项

以下内容可标「待确认」带入下游，不阻塞门禁：

| 项 | 处理方式 |
|---|---|
| 具体数值指标（例如提升 X%） | PRD 中标注待确认 |
| P1 与 P2 功能细节 | 只列功能名称 |
| 异常路径细节 | 标注需进一步细化 |
| 数据字段级别要求 | 只列核心对象 |

### 4.5 门禁决策规则

| 门禁结果 | 动作 |
|---|---|
| 未通过 | 自动继续下一轮追问，不询问用户 |
| 通过 | 必须询问是否继续追问（选项式），停止决策权交还用户 |
| 用户选继续 | 进入下一轮，重新评估门禁 |
| 用户选停止 | 汇总需求确认表，进入显式确认 |
| 进入 PRD 或原型生成前 | 必须获得用户对最终确认表的显式确认 |

显式确认信号分三类：

| 类别 | 信号示例 | 处理 |
|---|---|---|
| 白名单（推进） | 确认、通过、可以、同意、进入下一步 | 直接推进 |
| 灰名单（二次询问） | 看起来不错、差不多、先这样吧、没意见 | 追问一次是否确认通过 |
| 黑名单（不推进） | 修改、不对、暂停、再看看、有问题 | 回到修改流程 |

## 5. 选项化提问硬性规范

| 编号 | 规则 | 说明 |
|---|---|---|
| Q1 | 选项不超过 4 个 | 用 A / B / C / D 标注 |
| Q2 | 末位固定兜底 | 最后一个选项固定为「D) 其他__」 |
| Q3 | 选项互斥 | 需多选时显式标注「可多选」 |
| Q4 | 选项用具体业务内容 | 「A) 提升会员复购率」优于「A) 业务增长」 |
| Q5 | 数值类用区间 | 「A) 低于 10%」「B) 10%-30%」「C) 30%-50%」 |
| Q6 | 确认类也给选项 | 「A) 对」「B) 大方向对但有偏差」「C) 不对」「D) 其他__」 |

## 6. 用户可见输出规范

每轮追问固定输出三段，缺一段视为本轮未完成。

| 段落 | 内容要求 |
|---|---|
| 需求成熟度判定 | 给出级别（如 L1 草稿级）、判定依据、预计追问轮数 |
| 本轮追问重点 | 一句话说明本轮聚焦的维度 |
| MRC 状态 | 列出已通过门禁与未通过门禁，未通过项注明下一步追问方向 |

## 7. 追问停止条件汇总

| 编号 | 条件 | 后续动作 |
|---|---|---|
| C1 | MRC 门禁全部通过且用户选停止追问 | 输出需求确认表 |
| C2 | 用户对确认表给出显式确认（白名单信号） | 进入 02 段产品结构 |
| C3 | 用户选继续追问 | 回到追问循环，重新评估门禁 |
| C4 | 用户对确认表提出修改 | 输出变更影响说明，修订后重新等待显式确认 |
| C5 | 仍有未解决冲突项 | 冲突必须解决，不因停止追问而跳过 |

## 8. 与六段链路的衔接

| 本文件产出 | 交给下游的内容 |
|---|---|
| 需求成熟度与追问轮次 | 02 段产品结构的详略程度 |
| L1 表层诉求与 L2 真实痛点 | 02 段目标与非目标、用户角色 |
| L3 目标价值 | 02 段成功判断标准、06 段评分依据 |
| MRC 门禁状态与待确认项 | 02 段「待确认事项」 |
| 需求确认表 | 02 段页面清单的输入 |

## 9. 追问轮次控制

| 情形 | 处理 |
|---|---|
| 补问达到 2 轮仍不足 | 按红线 R3 写入待确认事项并继续推进，不无限等待 |
| 用户明确表示无补充 | 记录该维度为待确认，停止追加 |
| L0 需求预计超过 5 轮 | 拆为两批追问，第一批只做 L1 与 L2 痛点 |

## 10. 脱敏要求

确认表与追问记录中不出现真实姓名、完整手机号、身份证号、具体门牌地址、账号密码与 token。处理方式：需求描述列用脱敏值并在来源列标「已脱敏」，凭证类内容完全移除。

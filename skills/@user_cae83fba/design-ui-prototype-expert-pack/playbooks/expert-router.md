# 设计 UI 原型专家路由手册

## 总目标
把用户提供的 PRD、需求说明、产品想法、流程草图或现有页面，转化为可评审、可落地、可验收的 UI 原型与前端交接资料。执行时优先保证目标对齐、路径完整、状态清楚、交付可用，而不是堆砌视觉形容词。

## 通用执行契约

以下契约对 01 至 06 六个专家文件一致生效。专家文件只写本段特有内容，不再重复这三条。

### 通用追问触发条件

命中任一条即先追问，追问总数控制在 3 至 5 个：

- 当前阶段目标不清楚，用户未说明要解决什么任务。
- 用户没有说明输出用途，评审、开发交接与演示的产物不同。
- 缺少会改变关键判断的业务规则，例如角色、权限、数据来源、状态流转。
- 文件、页面、截图或链接无法读取。
- 用户要求超出本阶段边界的生产级交付。
- 用户输入跨多个阶段但未指明起点或终点。

### 通用信息缺失处理

- 缺失信息影响主路径或关键决策时，先提出必要问题，不进入主交付。
- 缺失信息不影响初版判断时，允许带假设推进，输出须分区标注「已知事实 / 合理假设 / 待确认事项」，并写明假设的影响范围。
- 不得把推测写成事实，不得用行业惯例替代用户确认的业务规则。
- 降级交付时给出四项：当前可确认信息、信息缺口清单、需要补充的材料、可继续推进的最低版本。

### 通用输出契约

每次输出必须包含五项，缺任意一项视为交付不完整：

- 本阶段结论，一句话可复述。
- 结构化表格或清单，字段名与 `data/schemas/` 中的 schema 属性名一致。
- 风险与待确认问题，含影响范围。
- 下一阶段建议，含建议进入的专家编号。
- 本段特有的补充段，例如复用边界、参数建议或评分依据。

### 通用质量门槛

- 没有 P0 阻断项。
- 主路径或主交付目标可被评审者独立复述。
- 关键状态、边界和假设被清楚说明。
- 必需输入字段齐备，缺失项已按 `references/error-codes.md` 的 E 码登记。

## 专家路由工作流

1. **需求到产品结构专家**：识别业务目标、用户角色、场景、页面清单、功能模块、主流程、分支流程、异常状态、权限边界和评审风险。
2. **流程到线框图专家**：为每个关键页面确定页面目标、信息优先级、区块结构、主次操作、状态覆盖和低保真交互说明。
3. **线框图到 UI 规格专家**：确定视觉风格、色彩、字体、间距、组件样式、页面密度、响应式适配和可读性标准。
4. **UI 到设计系统专家**：沉淀设计 token、组件规范、组件状态、复用规则和前端可落地的变量建议。
5. **UI 到前端交接专家**：输出组件拆分、状态机、字段、接口依赖、埋点建议、响应式规则、原型文件结构和交互说明。
6. **原型 QA 评审专家**：从产品、设计、前端、交付四个维度验收，明确通过项、问题项、修复建议和未覆盖风险。

## 路由规则

- 用户只有想法或 PRD：从 01 专家开始。
- 用户已有流程：从 02 专家开始，但先补齐角色、目标和异常状态。
- 用户已有线框：从 03 专家开始，但先检查页面目标和信息优先级。
- 用户已有 UI 图或 UI 说明：从 04 或 05 专家开始，取决于目标是沉淀规范还是交付研发。
- 用户要求“做个可点的原型”：至少执行 05 和 06，并说明原型不是生产级代码。
- 用户要求“帮我检查原型”：直接执行 06，同时倒查 01-05 是否有缺口。

## 质量原则

- 不用抽象漂亮话替代页面结构和状态说明。
- 不用视觉效果掩盖产品路径缺失。
- 不用代码片段冒充可运行原型。
- 不把设计系统写成颜色清单，必须有 token、组件、状态和使用规则。
- 不把前端交接写成页面描述，必须包含组件、状态、字段、接口、埋点、响应式和验收点。

## 参考资料使用

- 新手任务先读 `README.md` 段五与段六。
- 需要模板时读 `references/output-templates.md`，实体模板在 `templates/`。
- 产品与线框任务读 `references/product-wireframe-playbook.md`。
- UI 与设计系统任务读 `references/ui-design-system-guide.md`；需品牌参照时读 `references/brand-token-index.md`。
- 前端交接与原型任务读 `references/frontend-prototype-qa-guide.md`；QA 任务读 `qa/delivery-checklist.md`。
- 遇到方向跑偏时读 `references/anti-patterns.md`。

## 中文专家路由决策表

| 用户输入 | 优先进入专家 | 判断理由 | 不应做什么 |
|---|---|---|---|
| 只有一句想法 | 01 需求到产品结构专家 | 先确认目标、用户、页面和流程 | 不直接做 UI |
| 有 PRD / 会议纪要 | 01，再进入 02 | 先拆页面和状态 | 不跳过异常和权限 |
| 有流程或页面清单 | 02 流程到线框图专家 | 需要确认信息结构和操作路径 | 不先做视觉包装 |
| 有线框图 | 03 线框图到 UI 规格专家 | 需要转成可执行视觉规则 | 不只写抽象风格词 |
| 有多个 UI 页面 | 04 UI 到设计系统专家 | 需要沉淀 token 和组件状态 | 不只给审美评价 |
| 需要前端交接 | 05 UI 到前端交接专家 | 需要字段、事件、状态和数据假设 | 不承诺生产级代码 |
| 有 HTML / 原型文件 | 06 原型 QA 评审专家 | 需要证据化验收 | 不读取文件不能声称通过 |

## 输出总原则

- 先稳住当前阶段目标，再决定是否进入下一阶段。
- 所有结论都要区分事实、假设和待确认项。
- 面向中文普通用户表达，避免把内部专家名当成主要说明。
- 如交付物不足以进入评审，应明确降级交付，而不是包装成完整结果。
